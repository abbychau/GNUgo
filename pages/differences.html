How this repository differs from GNU Go 3.8

GNU Go 3.8, released by the GNU project on 17 February 2009, is the last official release. This repository starts from the 3.8 sources and brings the build, platforms and tests up to date. The engine is still GNU Go 3.8: the same pattern databases, the same reading and the same GTP commands, with a few small fixes.

In short: it plays like GNU Go 3.8 and still reports version 3.8. What changed is how you build, test and use it: CMake instead of autotools, ready-made programs for Windows, Linux and macOS, a WebAssembly build that runs in web pages, and automated tests on every change.

Engine changes

Only these changes touch the engine. Everything else, including the pattern databases, owl and tactical reading, influence, joseki and fuseki, the Monte Carlo mode, the GTP commands and the command-line options, is as in 3.8.

An owl pattern condition that never applied

Pattern VA32 in owl_vital_apats.db has a constraint written as !oplay_attack(*,?,b,*)==WIN. It is parsed as (!oplay_attack(…)) == WIN, which is always false, so the condition added in GNU Go 3.5.5 never took effect. It now reads != WIN.

Effect: no change in the results of the 11 main suites, nor of ld_owl and owl1.

A larger reading budget in fast_disconnect()

The quick check for whether two strings can be cut used a quarter of the connection reading budget. That was so little that the search often stopped at once and answered “can be cut” by default. It now uses half the budget.

Effect: the 11 main suites give the same counts with either budget. It can change the move chosen in some positions.

Undefined behavior

Modern compilers, and WebAssembly in particular, broke on code that older compilers happened to accept:

  • gg_sort() computed an out-of-range pointer when sorting zero elements. With clang this crashed genmove.
  • The random number generator shifted a negative signed integer.
  • The SGF reader moved a pointer before the start of its buffer when trimming an empty property value.
  • A Windows socket macro relied on defined inside a macro expansion.
  • Two global tables were defined in a header, which newer compilers reject as duplicate definitions.

Effect: none on play. Every fix keeps the same results; the main suites now run clean under UndefinedBehaviorSanitizer.

Smaller Monte Carlo pattern tables

The tables used by the experimental Monte Carlo mode are stored as a short list of distinct values plus one byte per entry, and expanded to the original values at startup.

Effect: the program is about 2.5 MB smaller (the WebAssembly module went from 6.1 MB to 3.6 MB); Monte Carlo play is unchanged.

Running one GTP command at a time

The GTP loop was split so that a program can initialize the engine once and then send single commands (play_gtp_init(), play_gtp_execute(), gtp_execute_line()). The WebAssembly build uses this. The GTP protocol itself is unchanged.

GNU Go in web pages

The biggest addition is a WebAssembly build. The whole engine, pattern databases included, is compiled to a 3.6 MB module (about 1 MB to download) that runs in a Web Worker, so the page stays responsive while GNU Go thinks.

  • A demo page: play on 9×9, 13×13 or 19×19 with handicap and a time limit, ask for hints, estimate the score, see dead stones and territory, and save or load SGF files. The game is kept in your browser.
  • A JavaScript API with promises (genmove, play, undo, finalScore, topMoves, any GTP command), a way to stop a long search, and SGF import and export.
  • TypeScript types and an npm package, @abbychau/gnugo-wasm, attached to each release and published to GitHub Packages.
  • The ordinary command-line program also runs under Node.js.

CI checks that the WebAssembly and native builds choose exactly the same moves in seeded games, so the browser version plays like the desktop one.

Building

  • The autotools files (configure, Makefile.am, …), the Visual Studio 6 projects and the old Windows config files are gone. CMake builds every platform.
  • CMakePresets.json has release, debug, ubsan and wasm builds: cmake --preset release, cmake --build --preset release, ctest --preset release.
  • The WebAssembly build needs only the Emscripten SDK: the pattern compilers are themselves compiled to WebAssembly and run under Node.js during the build.
  • cmake --install installs the program and the man page; --target manual builds the HTML and Info manual.
  • Compile-time options are still set in config.h.cmake.

Testing

  • tests/run_tests.py runs the regression suites with nothing but Python 3, in parallel, and compares the results with a stored baseline.
  • The 11 main suites (tactics, reading, owl, connection, semeai, endgame, capture, 13×13, strategy and more: 831 expected passes) are CTest tests.
  • Every push is built and tested on Linux, macOS, Windows and WebAssembly, plus a build with UndefinedBehaviorSanitizer that fails on any undefined behavior.
  • The original shell, awk, Perl and Pike tools still work and are kept in contrib/regress/.

Compatibility

  • GTP and GMP clients work exactly as before: the commands, responses and command-line options are the same.
  • The program still reports GNU Go 3.8. Releases of this repository are numbered 3.8.1 and up.
  • The license is unchanged: GPL version 3 or later, with the more permissive licenses of the GTP and GMP files as in 3.8.

The full list of changes is in NEWS and the commit history. The original project is at gnu.org/software/gnugo.
